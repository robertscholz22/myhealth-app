# MyHealth — Project Brief for Planning

Author: Fable 5.1 (lead), for the Opus planning agent. Date: 2026-09-12.
Owner: the developer (single user). Target device: Google Pixel 7A (Android 14+/15/16, Tensor G2, 8 GB RAM, 1080x2400, 6.1"). Owner is in Germany (assume German + English food labels, metric units, 24h clock, ISO week starting Monday).

## 1. Product vision (verbatim goal from the owner)

> I want an Android app for my Google Pixel 7A. It is supposed to serve as my central tracking hub for sport performance (soccer training and matches, running PRs), calorie and nutrient intake and general health. I have a Garmin watch and Garmin Connect on my phone, the app should use the Garmin data. I want to be able to create and maintain training plans across sports types (again soccer, running, strength training) and create calendar events like football matches and official runs and connect them to my Garmin activities. I also want to be able to register my standard meal ingredients and their nutrition values by scanning the nutrient table using my phone camera or by entering the values by hand. I want to be able to create meal templates and track meals in the calendar. My nutrition targets (calories, protein/carbs/fat split, etc.) should adapt to my weight, ideal weight and daily activities. My training plan should offer automatic suggestions for training sessions depending on my personal goals, my health and performance state and the events in my calendar.

Single user, personal app, sideloaded via adb (no Play Store). Offline-first: everything must work without network except explicit sync/lookup features.

## 2. Hard decisions already made (do not re-litigate; refine only)

### 2.1 Tech stack
- Kotlin, Jetpack Compose + Material 3, single Gradle module `:app` (multi-module is not worth it here) but strict package layering: `data/` (Room, repos, external sources), `domain/` (pure Kotlin models + engines, NO Android imports, fully unit-testable), `ui/` (Compose screens, ViewModels), `sync/` (WorkManager), `di/`.
- **No Hilt/Dagger.** Manual DI via an `AppGraph`/`AppContainer` singleton created in `Application`. Reason: fewer annotation-processor moving parts for agents to break; project is single-module.
- Persistence: Room (KSP), with exported schemas + migrations from day 1. DataStore (preferences) for settings.
- Navigation: `androidx.navigation:navigation-compose` with type-safe (Kotlin serialization) routes.
- Background: WorkManager (periodic Health Connect sync, target recomputation).
- Charts: Vico (`com.patrykandpatrick.vico:compose-m3`) — small and Compose-native.
- Camera/OCR: CameraX + ML Kit Text Recognition v2 (Latin, bundled) for nutrition labels; ML Kit Barcode Scanning + Open Food Facts API (free, no key) as a second way to add ingredients. OCR result must always land in an editable form (never auto-save unreviewed).
- Networking: OkHttp + kotlinx-serialization (no Retrofit needed; keep it lean).
- Testing: JUnit4 + kotlin-test/Truth for the domain layer (this is where the value is: nutrition math, training-load math, suggestion rules, OCR label parser); Room instrumented tests are optional; Compose UI tests minimal.
- minSdk 34 (Pixel 7A ships Android 14+; Health Connect is a platform component from 14). targetSdk/compileSdk 35 (installed SDK platform is android-35). Do not require platform 36 unless the bootstrap proves it is downloadable and needed.
- Language: app UI in English (owner's request text is English); food label parser must handle German and English label vocabulary.

### 2.2 Garmin data strategy (three tiers)
There is **no official personal Garmin API** (Garmin Health API is for legal entities only). Therefore:

1. **Tier 1 — Health Connect (primary, must-have).** Garmin Connect (Android, since 2025) writes one-way into Health Connect: exercise sessions (type, duration, distance, calories, HR samples, speed/cadence where available), steps, active/total calories, heart rate, resting HR, sleep sessions with stages, weight/body fat, floors, respiration, SpO2. NOT available via Health Connect: Body Battery, stress, HRV status, training load/status, VO2max, training readiness. The app reads Health Connect with the `androidx.health.connect:connect-client` 1.1.0 SDK, uses changes-tokens for incremental sync, stores a normalized copy in Room, and treats Health Connect as the source of truth for anything it provides. Must handle: permission flow, "Health Connect not available/needs update", rate limits, and the 30-day read-history limit for historical reads (initial backfill must request `PERMISSION_READ_HEALTH_DATA_HISTORY`).
2. **Tier 2 — Garmin Connect export import (must-have, cheap).** Manual import of Garmin's activity CSV export and FIT files (via the Android document picker / share-sheet intent). Use the official `com.garmin.fit:fit` Java SDK for FIT parsing (it is on Maven Central) — this gives full per-activity data including laps, HR, running dynamics, and for soccer/team-sport activities the GPS track. This is the fallback if Health Connect data is thin.
3. **Tier 3 — Direct Garmin Connect client (optional, last phase, clearly isolated).** Reimplement the SSO flow used by `garth-ng`/`python-garminconnect` (OAuth1 consumer → OAuth2 token exchange, MFA prompt) in Kotlin to fetch Body Battery, HRV, stress, training readiness, VO2max, training status. It is brittle (Garmin broke it in March 2026) so it must be a fully optional module that degrades gracefully: all engines must work without it. Credentials in EncryptedSharedPreferences/Keystore. Plan it, but implement it LAST and only after everything else is solid.

The domain layer must be source-agnostic: `ActivitySession`, `DailyHealthSummary`, `SleepRecord`, `BodyMeasurement` etc. carry a `source` field (HEALTH_CONNECT / FIT_IMPORT / GARMIN_API / MANUAL) and a stable `externalId` for de-duplication across sources (same activity may arrive from HC and from FIT import).

### 2.3 Domain engines (pure Kotlin, well-tested — this is the heart of the app)
- **Nutrition target engine.** Inputs: profile (sex, birth date, height), latest weight (from HC or manual), ideal/goal weight, goal pace (kg/week, bounded ±1 kg/week), activity level baseline, today's actual energy expenditure from Health Connect (total calories, or BMR estimate × activity factor when HC is missing), planned training for the day (from the calendar/plan) for *forward-looking* targets. Compute BMR (Mifflin-St Jeor), TDEE, calorie target with deficit/surplus capped for safety (never below ~1.2×BMR for deficit floor logic — the planner should specify sane clinical bounds), protein target in g/kg (higher on training/deficit days, e.g. 1.6–2.2 g/kg), fat floor (~0.8 g/kg or 20–35% energy), carbs fill the remainder, with a higher-carb bias on match day and the day before (carb loading for soccer). Also fibre, sugar, salt guidance and water. Must expose an explanation string ("why is this my target today") for transparency.
- **Training load / performance state.** From activity sessions: session TRIMP (Banister, from HR samples and HRmax/HRrest) with fallbacks (RPE × duration when no HR), acute (7-day) and chronic (28-day) load, ACWR, monotony/strain (Foster). Recovery state from sleep duration/quality, resting HR trend vs 30-day baseline, optional Body Battery/HRV if Tier 3 exists. Running performance: PRs per standard distance (1k, 5k, 10k, HM, M) detected from activities, plus best-effort estimation from any run (fastest split windows from FIT data when available). Soccer: minutes played, matches/trainings per week, high-intensity load proxy.
- **Training suggestion engine.** Rule-based, deterministic, explainable (no LLM, no network). Inputs: goals (e.g. "5k under 20:00 by 2026-11-15", "be fresh for matches", "gain strength"), calendar (matches, official races, planned sessions, blocked days), current load/recovery state, sport mix preferences (sessions/week per sport), constraints (no hard runs the day before a match, taper before races, ≥1 rest day/week, strength not within 48h before a match). Output: a proposed week (list of `SuggestedSession` with sport, type, target duration/intensity, rationale) that the user can accept/edit into the plan. Must include a simple periodization model (base/build/peak/taper toward a target race, in-season maintenance for soccer).
- **Meal/ingredient math.** Ingredients store nutrition per 100 g / per 100 ml / per piece; meals are templates of (ingredient, quantity, unit); logged meals are instances (template copy or ad-hoc) tied to a date/time and meal slot; daily totals vs targets.
- **Nutrition label parser.** From ML Kit text blocks to a `NutritionFacts` draft: handle German ("Brennwert kJ/kcal, Fett, davon gesättigte Fettsäuren, Kohlenhydrate, davon Zucker, Ballaststoffe, Eiweiß, Salz") and English ("Energy, Fat, of which saturates, Carbohydrate, of which sugars, Fibre, Protein, Salt / Sodium"), per-100g vs per-serving columns, comma decimals, `<0,5 g`, kJ→kcal. Tested with fixture strings.

### 2.4 Calendar
One unified calendar (day/week/month views) that shows: events (soccer match, soccer training, official run/race, other), planned sessions from the training plan, completed activities (from Garmin), logged meals, and daily summary (calories in/out, sleep). Events can be linked to an activity (manual link + automatic suggestion by time overlap + sport type). Recurring events (weekly soccer training) are needed. Optional later: read-only import from the device calendar via CalendarContract.

### 2.5 Explicitly out of scope for v1
Cloud sync, multi-user, Wear OS app, social features, Play Store release, iOS, Garmin Connect IQ watch app, AI/LLM features, writing data back to Garmin.

## 4. What the plan must contain
Write it to `~/my_health/docs/PLAN.md`. It will be executed by coding agents (Opus for complex/architectural tasks, Sonnet for well-specified mechanical tasks) working one task at a time on this machine, verified by the lead. Therefore:

1. **Architecture section**: package layout, module boundaries, threading/coroutine conventions, error handling conventions, how DI is wired, naming conventions, where tests live. Keep it short and prescriptive.
2. **Data model**: every Room entity with fields/types/indices and relationships; domain models where they differ from entities; enum lists (sport types incl. SOCCER_MATCH, SOCCER_TRAINING, RUN, STRENGTH, …; event types; meal slots; sources). Define the de-duplication key for activities.
3. **Engines**: precise formulas and rules for the nutrition target engine, training load, recovery state, suggestion engine, label parser — concrete enough that a Sonnet agent can implement them from the spec without design decisions, and with named test cases.
4. **Screens**: list of screens with their purpose, main state, and navigation graph (Home/Today dashboard, Calendar, Training Plan, Activities, Nutrition (diary), Ingredients, Meals/Templates, Add-by-camera flow, Body & Health, Goals, Settings/Integrations). Keep UI pragmatic: Material 3, bottom navigation, no custom design system.
5. **Phased task list** (the core deliverable). Ordered phases; within each phase, tasks numbered `P<phase>.<n>`. Each task: title, model (`opus` or `sonnet`) with one-line justification, files to create/modify, precise acceptance criteria (commands that must pass, tests that must exist), dependencies on other tasks, estimated size (S/M/L). Tasks should be sized so one agent can finish one in a single run (~≤ 25 files touched). Suggested phase order: P0 bootstrap → P1 core data + profile + settings → P2 Health Connect sync + activities screen → P3 calendar & events & linking → P4 nutrition (ingredients, OCR/barcode, meals, diary, targets) → P5 training load/recovery/PRs → P6 training plans + suggestion engine → P7 FIT/CSV import → P8 polish (charts, widgets?, backup/export to JSON) → P9 optional Garmin direct client.
6. **Verification strategy**: what the lead runs after each task (gradle build, unit tests, lint, apk size), and a manual smoke-test checklist for when the phone is attached (Health Connect permission grant, OCR on a real label, etc.).
7. **Risks & mitigations**: Health Connect data gaps, Garmin export formats, OCR quality, version pairing, and how each is handled.

Be concrete, avoid fluff, and prefer tables and bullet lists. Target 1500–3000 lines is fine if the content is dense; do not pad.
